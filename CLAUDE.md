# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Medici App is a Rails 8 healthcare application that connects patients with clinical trials in Colombia. It manages sponsors, trial center facilities/branches, studies, eligibility criteria, and patient enrollment/tracking through a trial's lifecycle.

## CI

CI (`.github/workflows/ci.yml`) runs four jobs on every PR and push to `main`: Brakeman, importmap audit, RuboCop, and **the full RSpec suite** (`test` job: Postgres service container, Chrome for the `js: true` feature specs, `dartsass:build` for CSS, and — critically — `yarn install`, because five importmap pins (trix, @rails/actiontext, @rails/activestorage, bootstrap, bootstrap-icons) are served out of `node_modules` via Propshaft asset paths; without them the browser's ES-module graph fails and every JS-driven feature spec breaks while the rest of the suite stays green (exactly the failure CI showed until 2026-07-18).

## Testing

- Feature specs (`spec/features/`, Capybara/headless Chrome) are reserved for behavior that genuinely needs a browser (JS gating, Stimulus) — cover everything else with request specs.

## Architecture

### Authentication & Authorization

- **Devise** handles authentication on `User`, with a custom `users/sessions` controller (`app/controllers/users/`).
- **Nobody self-registers. `User` is deliberately NOT `:registerable`** — the sign-up routes, `Users::RegistrationsController` and its views do not exist. Staff accounts (admins, sponsor reps, trial centre reps, platform staff) are created by an admin through the role-specific controllers. **Do not re-add `:registerable`** to "fix" a missing sign-up page; there isn't meant to be one.
- **Patients have NO accounts at all** (changed 2026-07-15 — an earlier version of this file described the opposite and told you not to change it; that guidance is obsolete). A patient is a plain record, never a `User`:
  - **Public route:** "¡Quiero participar!" → `ParticipationRequestsController` (`GET/POST /studies/:study_id/participate`, public, no login). It captures a **contact number and/or email** plus the study, and creates a `Patient` (AASM `prospect`) and a `Consent`. Nothing clinical is accepted here — the permitted params are only `:contact_number, :email`.
  - **Staff route:** a trial centre rep or admin builds the real clinical record via `PatientsController` (the full form).
  - **The Ley 1581 authorization is still a hard gate** on the public form: leaving a phone number against a *named clinical trial* says something about your health, so nothing at all is written until it is granted. See `ParticipationRequestsController#create`.
  - `Patient belongs_to :study` (`patients.study_id`) — **one study per patient**. This used to live on the patient's `User` via the `studies_users` HABTM; that join is now staff-only.
  - `Consent belongs_to :patient` (not `User` — there is no account to hang it on).
- **Pundit** handles authorization (`app/policies/`). `ApplicationController` includes `Pundit::Authorization`. Two distinct mechanisms, easy to confuse:
  - **`authorize`** answers *may this role touch this resource at all* — wired generically by the `ResourceAuthorization` concern, which authorizes the **model class, not the instance**. So overriding `show?`/`update?` to inspect `record` as an instance silently never fires for standard actions.
  - **`policy_scope`** answers *which rows* — this is where row-level rules belong. `PatientsController` loads **every** action through it (including member actions), so an out-of-reach patient **404s rather than 403s**: a 403 would confirm the record exists, which is itself a disclosure about an identifiable person.
- `SecureApplicationController < ApplicationController` adds `before_action :authenticate_user!`; controllers that require login inherit from it instead of `ApplicationController` directly.
- **Account activation gate (`users.active`, added 2026-07-22).** A staff account is **inactive by default** (`default: false, null: false`) and **cannot sign in** until an admin switches it on: `User#active_for_authentication?` is `super && (active? || admin?)`. Devise checks that predicate at sign-in *and* on every request (`Devise::Hooks::Activatable`), so deactivating somebody also ends the session they already hold. **Admins are always active** — `before_save :force_active_for_admins` rewrites the column on every save and the `|| admin?` carve-out means even a direct DB write can't lock the people who operate the manager out of it. The migration backfilled **admins only**; every pre-existing rep/platform-staff account starts inactive and must be activated deliberately.
  - The manager is `UserActivationsController` (`/user-activations`, index + update), admin-only via `UserPolicy#manage_activation?` — deliberately **outside** the permission matrix, same reasoning as `RolePolicy` (a role that could grant sign-in to other accounts is a privilege-escalation path). It overrides `authorization_model` to `nil` (no `UserActivation` model) and authorizes explicitly. Filters: account kind, sponsor, trial-centre branch, active/inactive, name/email search — an organisation filter implies its account kind and wins over a conflicting `type`.
  - **Specs create active users by default** (`spec/factories/users.rb` sets `active { true }`); use the `:inactive` trait to exercise the gate. Without that default every signed-in request spec would be bounced by the Devise hook.
- `PaperTrail` is included in the Gemfile for auditing/versioning (check individual models for `has_paper_trail` before assuming a model is versioned).

### User / Role Model (delegated_type, not enum or STI)

`User` is the Devise-authenticatable identity, but role-specific data lives on separate models via Rails' `delegated_type`:

```ruby
delegated_type :userable, types: %w[SponsorRep Admin Patient TrialCenterBranchRep PlatformStaff], dependent: :destroy
```

- **`Patient` is still listed as a type, but no patient User exists any more** (see above — patients have no accounts, and `RemovePatientUserAccounts` deleted the last ones on 2026-07-15). In practice `user.patient?` is always false and `User.patients` is always empty. The type is left in place so the delegated_type stays truthful about the column's history; **do not build new features on the assumption that a patient can log in**. Count patients with `Patient.count`, never `User.patients.count`.
- The `Userable` concern lives at `app/models/userable.rb`, NOT `app/models/concerns/` — Zeitwerk won't find it where you'd first look.
- Role checks are plain predicate methods on `User` backed by `userable_type`, not an enum column — **do not add a `role` enum**, extend the existing delegated-type pattern instead.

### Patient Lifecycle (AASM state machine)

`Patient` uses **AASM** (not a plain enum) to track trial participation status — states and events live in `app/models/patient.rb`, and the forward transitions are **guarded** (see the recruitment-score section below), so writing `state` directly bypasses a clinical gate.

**The first state was renamed `prospect` → `interested` on 2026-07-22** (sales language for somebody who raised their hand about a trial). The lifecycle is otherwise unchanged. The rename went through the DB (column default + a data migration on existing rows), the AASM definition, `RecruitmentProgress::STATES`, the `seg-*` / `dot-*` / `patient-state--*` SCSS classes (they are generated from the state name — renaming one without the other silently drops the color), and the `patients.states.*` / `studies.recruitment.*` locale keys in all four languages. **PaperTrail versions deliberately still contain `"prospect"`** — an audit trail records what a value was called at the time.

### Core Domain Model

- **Study** still HABTMs `User`, but that join no longer carries patients (staff-only) — patients hang off `patients.study_id` directly.
  - **`study_type` (added 2026-07-22, required)** — `observational` / `interventional`, a string-backed enum like the others. It is **not** a cosmetic label: it decides which of the two approval booleans the study is judged by (`Study#approval_attribute`). Observational research assigns no intervention, so the sign-off is the ethics committee's (`committee_approved`); interventional research administers a drug/device, so it is the local health authority's (`local_health_authority_approved`). Both default `false`. Existing studies were backfilled `interventional` (they all carry a phase I–IV, which only interventional research has).
  - **There is no generic "new study" button any more.** The studies index renders `_new_study_dropdown` — one entry per enum value — and the type travels as `GET /studies/new?study_type=…`. `StudiesController#new` falls back to `interventional` for a missing/unknown value rather than rendering a form with no approval question. On `new` the type is a hidden field (chosen already); on `edit` it becomes a select, and switching it re-renders with the other approval question.
- **`LocalParameter`** (added 2026-07-22) — country-scoped configuration so jurisdiction-specific names stay out of the code: `belongs_to :country`, columns `name` (internal key) / `value` / `display_name` / `description`, unique per `[country_id, name]`, audited. `LocalParameter.health_authority_label` resolves `local_health_authority` for a country (defaulting to `LocalParameter::DEFAULT_COUNTRY_CODE`, `"CO"` — nothing in the schema gives a study a country, not even via facility/branch), which is how the interventional form asks "¿Aprobado por **INVIMA**?" instead of showing a raw key. Returns `nil` when unconfigured; the form then falls back to a generic translated label rather than rendering the key. Seeded idempotently by `LocalParametersSeeder` (wired into `db/seeds.rb`, and it creates Colombia if the countries seeder — which is disabled by default — never ran). Managed at `/local-parameters` by `LocalParametersController`, **admin-only via `LocalParameterPolicy` and deliberately outside the permission matrix**, same reasoning as `RolePolicy`.
- **Patient** — belongs to one **Study**. Reached from a centre via `Study ↔ TrialCenterBranch`: this chain (rep → branch → studies → patients) is what `PatientPolicy::Scope` walks, and `Patient.for_trial_center_branches` expresses.
- **`Study#trial_cities` is NOT `cities`** — the city↔study link for centres goes through branches (`City ↔ TrialCenterBranch ↔ Study`); `TrialCity` is a different, study-owned thing.

### Eligibility criteria engine (analyzed 2026-07-13; evaluator re-verified against the code 2026-07-15)

Three tables — `app/models/{criteria_profile,criteria_variable,variable_value}.rb` — plus the shared `CriteriaComparable` concern and the `EligibilityResult` PORO (`app/models/eligibility_result.rb`). Read those files for the mechanics; what follows is only what the code can't tell you.

- **At most one `CriteriaProfile` per study — enforced since 2026-07-31** by a partial unique index (`study_id IS NOT NULL`) plus a model validation, and `Study has_one :criteria_profile, -> { order(:id) }` so the answer is deterministic. This used to be an unwritten invariant. It matters because `has_one` emits `LIMIT 1` with **no `ORDER BY`**: with two rows the winner was physical row order and flipped when a row was merely updated — and since the profile gates promotion, a duplicate defining no primary criteria silently let patients through. Many profiles with `study_id: nil` are still fine (reusable templates).
- **`CriteriaComparable#satisfied_by?` returns `nil` — not `false` — for a blank/unparseable value**, so callers can tell "unknown" from "fails". An **unmeasured exclusion does not pass** — it surfaces as incomplete rather than as a silent pass. Both are load-bearing contracts; don't "simplify" them.
- **`CriteriaAssessmentsController` follows the patient sub-resource auth recipe as of 2026-07-31 — it did not before.** `set_patient` was a bare `Patient.find`, so any rep with the class-level `can_edit` permission could read *and write* any centre's patient criteria (its sibling controllers all 404 correctly). That went from a PHI leak to a forgeable eligibility gate once these values started gating promotion: a rep with no authority over the patient could write the values, flipping `primary_criteria_met?` to true so the patient's own rep could promote them. Now `policy_scope(Patient).find` + `authorization_model = nil`. `set_profile` is also locked to the patient's **own study's** profile (a mismatched `criteria_profile_id` 404s) so the page can never evaluate one rule set while the gate uses another.

**Gotcha (FIXED 2026-07-16) — answers now match rules by FK, not by `name`.** Historically `evaluate` did `patient.variable_values.index_by(&:name)` and looked up `cv.name`, with no FK linking the two, so **renaming a `CriteriaVariable` silently orphaned every existing patient answer** (a patient reading `eligible=true, complete=true` flipped to `missing` the moment the rule was renamed). Fixed by adding `variable_values.criteria_variable_id` (FK, `on_delete: :nullify`), backfilled by name within the patient's profile. `CriteriaProfile#evaluate` and the assessment upsert now key off the FK, falling back to `name` only for legacy rows written before the FK existed; every capture refreshes the snapshot `name` to the rule's current name. Deleting a rule nullifies the FK but leaves the answer's snapshot intact as a historical record. Guarded by `spec/models/criteria_profile_spec.rb` ("keeps the answer linked when the rule is renamed"). Renaming is safe now — but a `VariableValue` still keeps its own snapshot columns by design, so treat those as a point-in-time copy, not a live mirror of the rule.

**Recruitment score — primary vs secondary criteria (added 2026-07-31).** `criteria_category` (`primary` / `secondary`, on **both** `criteria_variables` and `variable_values`, default `"primary"`, `null: false`) splits the rules that *decide* from the rules that *inform*. It answers a different question from the verdict, and the two are allowed to disagree — surface both, don't collapse them:

- **`eligible?` / `verdict` = the protocol question** ("does this patient meet the protocol") and still weighs **every** criterion, unchanged.
- **`primary_score` / `recommendation` = the recruitment question** ("is there enough evidence to move them forward") and weighs **only the primary** criteria. `primary_score` is `passing primary / total primary × 100`, measured against *all* primary criteria rather than only the answered ones — an unmeasured criterion is not evidence in the patient's favour, so it holds the score down until somebody measures it. `nil` when the profile marks nothing primary.
- **`recommendation`** → `:ready` (100%, promote), `:promising` (≥ `HIGH_SCORE`, default 70, nothing decisive failed — worth a rep's attention), `:blocked` (**any** primary check fails; this wins regardless of how high the percentage is), `:pending` (too little measured), `:none` (no primary criteria → the UI falls back to the old `eligible?`-driven behavior). Thresholds are `EligibilityResult::READY_SCORE` / `HIGH_SCORE`.
- **`primary_verdict` = what the UI headlines** → `:eligible` / `:not_eligible` / `:incomplete` / `:none`, decided by the primary criteria alone. `verdict` (whole-protocol) is kept for reporting but is **deliberately no longer the banner**: a patient held up only by a complementary criterion must not be shouted at as "not eligible". Secondary failures render as a separate **warning** (`_secondary_warning.html.erb`) that names them SECONDARY and says the rep decides whether they matter.
- **`permits_promotion?` is a HARD GATE, not advice (2026-07-31).** A patient moves forward only when **every primary criterion has a recorded value and all of them comply** — unmeasured is never compliance, so a rep must actually record each one. Enforced as an **AASM guard** on `assess`/`accept` in `Patient` (`guard: :primary_criteria_met?`), which is why it cannot be bypassed by any code path, and why it propagates for free: `PatientPolicy#assess?/#accept?` already delegate to `may_assess?`/`may_accept?`, so the policy, the controller and every view follow automatically. `PatientsController#transition` re-checks it only to produce a specific reason (`patients.primary_criteria_required`) instead of a bare "not authorized".
  - **Backward steps (`discard`/`reject`) are never gated** — walking a patient back must always be possible, especially when the criteria are what went wrong.
  - **No auto-transition.** The rep pressing the button *is* the recorded decision (PaperTrail versions the state change with the acting user). Secondary criteria are the rep's judgment call, expressed by making or withholding the transition.
  - **Two gotchas this created.** (1) Because the guard evaluates the profile, and `patients/index` asks `policy(patient).assess?` per row, `PatientsController#index` **must** eager-load `study: { criteria_profile: :criteria_variables }` + `:variable_values` or it N+1s. (2) `Patient#eligibility_result` is memoized per instance, so `Patient#reload` is overridden to drop the memo — otherwise a re-read after capturing values would still gate on the stale verdict.
  - **UI:** when the role permits the forward step but the criteria block it, the button renders **disabled with the reason** (`criteria_assessments.locked.hint`) rather than vanishing — which is what would otherwise happen, since the guard makes `policy.assess?` false.
- Migration backfilled every existing rule to `primary`, because before the split every enabled criterion counted equally — that's the only backfill that leaves existing profiles behaving as they did. `VariableValue` snapshots the category like it snapshots the rest of the rule (what was scored at the time must not change retroactively).
- **UI:** the capture form groups by category (primary first); `_verdict_banner`, `_secondary_warning` and `_score_card` under `app/views/criteria_assessments/` are **shared** by the assessment page and the briefing (they used to duplicate the banner and drifted); out-of-reach/pending entries carry a primary/secondary badge. Copy lives under `criteria_assessments.{score,primary,secondary_warning,locked}.*` (4 locales).
- **Seeds (rescaled 2026-08-24):** `db/seeds.rb` now seeds a **full development graph** and is guarded by `unless Rails.env.development? ... return` — everything below that line (staff accounts with the hard-coded password `12345678`, a few hundred fake patients) is one `heroku run rails db:seed` away from production otherwise, so **do not replace the guard with a comment**. Reference data (roles, categories, local parameters) still seeds in every environment. The dev graph: 20 trial-centre facilities + branches + reps, 15 sponsors + reps, ~42 studies with articles/contacts/results/categories/branches, ~370 patients spread across the lifecycle, and **one `CriteriaProfile` per study** from `db/seeds/example_criteria_profiles.rb` (4 therapeutic areas, cycled). Patients are seeded as plain `Patient` rows — the old `FactoryBot.create(:user, :patient)` and `User.patients.each` blocks seeded a model the app no longer has and were deleted. Cities come from a fixed Colombian pool (`Patient::PRINCIPAL_CITIES`), not `Faker::Nation.unique.capital_city`, which raises `RetryLimitExceeded` once a few dozen branches drain the unique pool.
- **Profile shape — the primary count is FIXED at 5 (2 inclusion + 3 exclusion), not a percentage of the protocol.** Both seeders build 25 criteria with exactly 5 primary. The reason is the questionnaire: the primary criteria *are* the questions a patient is asked, and that form must stay short enough to finish, so the ceiling is **6** whatever the protocol's size. 5 is also the smallest count that lets the score show its own thresholds — the score is `passing primary / total primary`, so with N primary the only reachable values are multiples of 100/N; with 2 you get 0/50/100 and `:promising` (the ≥70% band) can never occur, with 5, 80% lands in it. All 5 are deliberately **patient-answerable** (age, diagnosis, active infection, pregnancy, other-trial participation) because auto-triage fires only when declarations satisfy *every* primary criterion — a primary rule only an investigator can measure (HbA1c, VEF1, IGA, BSA%, all therefore secondary) would silently make auto-triage impossible. `db/seeds/example_seborrheic_dermatitis_profile.rb` keeps its worked example: `report!` builds one demo patient per recommendation, including the instructive `:ready` case, which scores 100% while the whole-protocol verdict is `not_eligible` because a *secondary* exclusion is triggered, and `:blocked`, which sits at 80% and is blocked anyway because one primary check fails.

**Patient self-report — two tiers of evidence (added 2026-08-01, Phase A of `docs/design_patient_self_report_2026-07.md` as re-scoped by the partners).** After the public participation form (step 1), studies with `patient_self_report_enabled` (default false — flipping it on means the question wording is CEI-approved participant material) send the patient to a **public step-2 questionnaire** (`SelfReportsController`, `GET/POST /studies/:study_id/participate/questions`):

- **Identity is the session, never params.** Step 1 stamps the new patient's id + expiry into the encrypted session; step 2 reads only that. Any failure (no stamp, expired, switch off, nothing askable) = redirect to root. One submission consumes the stamp.
- **A rule is askable only when it is PRIMARY *and* carries a `patient_prompt`** (`askable_to_patient`, tightened 2026-08-24 — it used to filter on prompt presence alone, so a secondary rule with a prompt was asked). Primary-only is enforced in the scope, not left to whoever writes the prompts: the questionnaire exists to triage, and only the primary criteria are scored, so a complementary question would lengthen the form without being able to move the outcome. Spec-pinned in `spec/requests/self_reports_spec.rb` ("never asks a secondary criterion, even one that has a prompt written") — the older fixture confounded the two reasons a rule goes unasked by being both secondary and promptless. The questionnaire renders the prompt and NOTHING else — never `name`, `rule_summary`, thresholds, or min/max on inputs, which would leak the protocol. No verdict is ever echoed back ("Gracias, el centro revisará…") — a verdict would make the form an oracle to optimise against. Both are permanent constraints.
- **Answers land in `patient_declarations` (testimony), NEVER `variable_values`.** The table deliberately lacks `comparison_type`/`reference_value_1/2`/`variable_type`/`criteria_category` and calls its column `answer` — structurally unscorable; anyone shortcutting the separation gets a `NoMethodError`. Scoring happens only by handing the raw answer to the LIVE rule (`CriteriaProfile#evaluate_self_reports` → `cv.satisfied_by?(answer)`), so re-editing a rule re-judges old testimony. Declarations are append-only (`supersede!`, `live` scope), `answer` encrypted + PaperTrail-skipped, "No sé" (`declined`) is a first-class non-answer. `recorded_by` nil = patient-entered; a staff user = phone/paper transcription.
- **Two-tier AASM guards:** `assess` (interested→candidate, *triage*) opens on investigator values **or** declarations (`primary_criteria_met_for_triage?`); `accept` (candidate→participant, *clinical*) opens **only** on investigator values. A patient can self-report onto the rep's review list, never into the trial. **`PatientsController#transition`'s friendly re-check must match the event's tier** (`FORWARD_EVENT_CHECKS`) — checking the clinical tier for `assess` wrongly refuses a rep assessing a self-report-qualified patient (bug caught 2026-08-01, spec-pinned).
- **Auto-triage:** on questionnaire submit, if declarations satisfy every primary criterion the system fires `assess!` under `PaperTrail.request(whodunnit: "system:self-report-triage")` — the audit trail says truthfully that the system did it. "Candidate" therefore contains unverified self-reports; the patients index orders candidates first, then by questionnaire fill count, so reps review them.
- **Uploads:** `patient.self_reported_files` (5 × 25 MB, pdf/images), server-side multipart attach only — the Active Storage **direct-upload login gate stays intact**. Named apart from the staff-curated `ComplementaryInformation` so provenance stays legible.
- **Step-1 additions:** `submitted_by_proxy` ("Yo no soy el paciente" — qualifies the consent, shown to reps) and `adult_confirmed` (hard gate — Ley 1581 Art. 7, minors). `reported_city` (plaintext, coarse) from a picker of `Patient::PRINCIPAL_CITIES` — deliberate: IP geolocation is unreliable on Colombian mobile CGNAT and third-party IP lookups are a new *transmisión*.
- **Consents:** submission records `ley_1581_self_report_questionnaire` (own version constant); the optional, visually-apart future-studies checkbox records `future_studies_matching`. Never bump the shared `LEY_1581_CURRENT_VERSION` for these.

**Key limitations (still true — the engine evaluates atomic rules only):**
- **Atomic only — no boolean composition.** Each variable is a single comparison, and `evaluate` implicitly ANDs them all. There is no AND/OR/grouping/nesting, so a compound rule ("severe = score ≥ 20 AND BSA ≥ 10%") must be split into several separate variables, and an OR ("candidate due to A *or* B") cannot be represented — only flattened to one boolean.
- **No temporal semantics.** "in the last 2 / 6 / 24 weeks" is descriptive text baked into the variable `name`; the engine compares a static value, never a date window.
- **No investigator-judgment / free-text criteria** as first-class — clinical catch-alls ("any condition that, in the investigator's opinion, …") can only be modeled as a single boolean flag the investigator toggles.

### Rich text / Action Text (added 2026-07-16)

**SOAP notes were REMOVED on 2026-08-24** (`DropSoapNotes`). The `SoapNote` model, `SoapNotesController`, its views, routes, factory, specs, the four `soap_notes.*` locale blocks and the `/about` manual entry are all gone. The only rich text left in the app is `ComplementaryInformation#notes`. Two things the drop migration had to do beyond `drop_table`, worth knowing if another rich-text model is ever retired: `action_text_rich_texts` is **polymorphic**, so its `record_type = 'SoapNote'` rows survive dropping the owning table, and so do the `active_storage_attachments` rows for each body's embedded images — both were deleted explicitly, leaving the blobs *unattached* so the normal daily sweep reclaims them (never purge S3 objects inline in a migration). PaperTrail `versions` rows with `item_type = 'SoapNote'` are **deleted by the same migration** — confirmed no production notes ever existed, so that history describes nothing that happened. (With real notes the call goes the other way: retiring a feature is not a reason to erase an audit trail.)

- **Action Text was installed 2026-07-16** (`action_text/engine` was required but not installed). Because this is a **Propshaft + importmap** app (no JS bundler), the pieces are wired the same node_modules way as bootstrap: `config/initializers/assets.rb` adds `node_modules/trix/dist` and `node_modules/@rails/actiontext/app/assets/javascripts` to the asset paths and precompiles `trix.esm.min.js`/`actiontext.esm.js`/`actiontext.css`; `config/importmap.rb` pins `trix` → `trix.esm.min.js` and `@rails/actiontext` → `actiontext.esm.js`; `application.js` imports both; the layout links `stylesheet_link_tag "actiontext"` (the sass-compiled `application.css` does not include Trix styles). **If you re-run any RSpec-touching Rails generator, it may force-overwrite `.rspec`/`spec/rails_helper.rb`** — the Action Text installer did; both were restored from git (they carry `pundit/rspec`, the support glob, and the Shoulda::Matchers config).
- **One upload path for file fields, as of 2026-08-24: plain multipart.** No `file_field` passes `direct_upload: true` any more — `ComplementaryInformation`'s PDF/image fields were the last two, and they now POST through the app for the controller to attach server-side, matching what the public self-report questionnaire already did. One mechanism to reason about, and every cap/content-type check lives in model validations on that one path. The tradeoff is deliberate: a multipart upload occupies the dyno for the whole transfer, so a 25 MB PDF on a slow connection is now bounded by Heroku's 30-second request timeout, where direct-to-S3 was not. If large-file timeouts appear, that is why.
- **Action Text still direct-uploads, and that is NOT optional.** `@rails/actiontext` registers a `trix-attachment-add` handler that runs an Active Storage **DirectUpload** from JS the moment an image is dropped/pasted into a Trix field; the body stores only the blob reference. This is not a `direct_upload: true` attribute and did not go away with them — the `/rails/active_storage/direct_uploads` endpoint, its `authenticate_user!` gate, the `@rails/activestorage` pin and `ActiveStorage.start()` in `application.js` all remain load-bearing. Active Storage uses the S3 service in production (`config.active_storage.service = :amazon`), so attachments land in the AWS bucket; `image_processing` is enabled for variants.

### ComplementaryInformation & the fused patient page (briefing merged in 2026-08-24)

- **`ComplementaryInformation`** (note the spelling — *complementary* = supplementary, not "complimentary"): its `update` **appends** files via `.attach` rather than assigning the collection (Rails 7.1+ **replaces** on assign — assigning would silently drop the previously uploaded exams).
  - **Design note (open):** the goal framed this as something "the patient provides", but **patients have no accounts** (hard rule), so it is currently a **staff-managed** surface. A patient-facing *public* upload page was deliberately **not** built — an unauthenticated file-upload endpoint needs an explicit product/security decision first.
- **The patient page is BOTH halves of the record (fused 2026-08-24).** `patients#show` renders demographics on the left and the clinical/eligibility picture on the right; `PatientBriefingsController` and `app/views/patient_briefings/` were deleted. They were two pages answering halves of one question ("who is this, and can they move forward?") and a rep had to bounce between them. The old URL is kept as a **route-level redirect** (`get "briefing", to: redirect("/patients/%{patient_id}")`) so bookmarks land somewhere useful; `patient_briefing_path` still resolves, and the `patient_briefings.*` locale keys are still used by the fused page — the content moved, it did not disappear. `PatientsController#show` now loads `@profile` / `@result` / `@complementary_information`, using the **memoized** `Patient#eligibility_result` so the AASM guards behind `policy(@patient).assess?` further down the page reuse one evaluation. The clinical column lists **every** criterion with its answer, primary block before secondary — the old briefing showed only failing and pending ones, so a rep could not see what a patient actually passed without opening the assessment form. `_patient.html.erb` is the demographic column and deliberately carries **no** lifecycle buttons: promotion is one decision and lives in the single take-action bar, where the reason it is or isn't available can be stated once.
- **`Patient::FORWARD_EVENT_CHECKS` + `Patient#criteria_permit_forward?` are the ONE source of truth for "do the criteria permit the next step" (moved off the controller 2026-08-24, fixing a live bug).** The map lived in `PatientsController` while three views hardcoded `!primary_criteria_met?` for BOTH forward events — so an `interested` patient who qualified only by self-report rendered a disabled "locked" button *next to* a working assess button. Anything asking that question must call `criteria_permit_forward?` rather than pick a tier predicate itself; `PatientsController#transition` reads `Patient::FORWARD_EVENT_CHECKS` for its per-tier refusal message.
- **Shared authorization pattern for the patient sub-resources** (complementary info, briefing, criteria assessment; `ComplementaryInformationsController` is now the reference implementation): each is gated by the parent patient's visibility, NOT the `PermissionCatalog` matrix. The recipe is `set_patient` via `policy_scope(Patient).find` (out-of-reach → 404) + explicit `authorize(@patient, :show?/:update?)` + **override `authorization_model` to return `nil`** so `ResourceAuthorization` doesn't try (and fail) to find the sub-resource's model in the permission matrix. Copy this recipe for any future patient sub-resource.

### Background jobs & Active Storage garbage collection (2026-07-18)

- **Jobs run in-process (`:async` adapter) in production.** There is no worker dyno; the app's only background jobs are Active Storage's own (analyze, purge) plus Action Text embed purges. `purge_later` therefore works, but a job pending during a dyno restart is lost — by design, because:
- **`PurgeUnattachedBlobsJob` is the safety net** (`app/jobs/`), run daily in production by **Heroku Scheduler** → `rails active_storage:purge_unattached`. It purges blobs with no attachment older than `TTL` (3 days): abandoned Trix uploads (images upload to S3 the moment they're pasted, before any submit), direct-upload files whose form failed validation or was never submitted, and blobs orphaned by lost purge jobs. **If the Scheduler job isn't configured, orphans accumulate silently** — that scheduled task is part of the design, not an optimization.
- **`rails active_storage:audit_orphans`** (report-only, never deletes) finds what the sweep can't: service files with no blob row, and blank rich texts still holding embeds (the pre-`store_if_blank` leak shape).
- **`store_if_blank: false` on every `has_rich_text`** (today only `ComplementaryInformation#notes`). Two distinct clear paths, verified empirically (2026-07-18): assigning `""`/nil destroys the RichText row (this option); a **browser** clear submits `"<div><br></div>"` — present, so the row survives and it's Action Text's embed re-sync (`RichText#before_save`) that detaches the images. Both end with the blobs unattached and sweep-reclaimable; don't weaken either assuming the other covers it. Keep the option on any future `has_rich_text`.
- **Open follow-up (found in review 2026-07-18, deliberately not in that PR):** the blob-*serving* engine endpoints (`ActiveStorage::Blobs::*`, `Representations::*`, `DiskController`) authenticate by signed URL alone, and `config.active_storage.urls_expire_in` is unset — so a leaked `rails_blob_path` link to a patient's clinical file works **forever**. Consider setting `urls_expire_in` (Action Text bodies store never-expiring attachable sgids, not URL signed_ids, so old notes keep rendering — verify that before shipping).
- **The direct-upload endpoint requires login** (`config/initializers/active_storage_direct_uploads.rb`): every upload surface is staff-only and the public participation form takes no files, so anonymous blob minting (an orphan/cost/abuse surface) is blocked. If a patient-facing upload flow is ever built (see the ComplementaryInformation design note), this gate must be revisited alongside it.

## Key Conventions

- Prefer extending the `delegated_type`/`Userable` pattern for new role-specific data rather than adding columns to `User` directly.
- Prefer AASM events over direct state-column writes for `Patient` status changes.
- Model files carry Rails schema-annotation comments (`# == Schema Information`) at the top — keep them in sync (the `annotate` gem manages these; don't hand-edit stale ones, just re-run annotate).
- **Name a patient with `Patient#display_name`, never `fullname` raw.** A patient who arrived through the public participation form has NO name — that form takes a phone/email and nothing else — so `fullname` is `""` for every lead and a view rendering it produces an empty cell, or an empty *unclickable link*. `display_name` falls back to `participant_code`. This was `fullname.presence || participant_code` copy-pasted at ten call sites until 2026-08-24; the study page was the one that forgot, which is how the bug was found.
- **Render an eligibility rule's badges with the shared helpers** — `criteria_category_badge(variable)` and `variable_type_badge(variable)` (`ApplicationHelper`), never inline markup. Between them they appear on four variable tables (`criteria_variables/index`, `criteria_variables/_criteria_variable`, `criteria_profiles/show`, `studies/show`) plus the study page's two Demográfico lists, and badges whose colour encodes meaning must not drift between the places a rep reads them. Both use Bootstrap 5.3 `-bg-subtle` / `-text-emphasis` token pairs (restyled 2026-08-24 from solid fills and a hand-rolled teal): a rule table is a dense grid and four saturated badges per row shout over the data they annotate. All four pairs clear WCAG AA comfortably (10.2–10.6:1, measured), and they swap correctly under a dark theme — the direction of task D4. **The two axes are deliberately different colours**: `variable_type` is green=inclusion / red=exclusion (does this let you in or keep you out), `criteria_category` is blue=primary / grey=secondary (does this decide anything). The study page's two variable lists also order **primary first**, via an explicit `CASE WHEN criteria_category = 'primary'` rather than relying on `'primary' < 'secondary'` sorting that way by accident.
- **The four rule-display helpers all live in `ApplicationHelper`** and every variable table uses all of them: `criteria_category_badge`, `variable_type_badge`, `boolean_checkbox(value, label:)` for the Habilitado/Mostrado flags, and `patient_prompt_display` for the patient question. The flags are **disabled checkboxes**, not Sí/No badges (2026-08-24): a checkbox scans faster down a column and, unlike a coloured badge, does not compete with the two badges on the same row that actually carry meaning. `disabled` rather than `readonly` because checkboxes ignore readonly, and these tables are never inside a form; the attribute name goes into `aria-label`/`title` since a bare checkbox in a grid tells a screen reader nothing. `patient_prompt_display` renders a muted em-dash when blank — blank is meaningful (it is what makes a rule un-askable), so it gets a visible placeholder rather than an empty cell.
- **Three tables show the same rule columns and must stay in step**: `criteria_variables/index`, `criteria_profiles/show` and the profile card on `studies/show`. They drifted before — `criteria_profiles/show` was missing the category column entirely and two of the three were missing the patient question. If you add a column, add it to all three, and check `<th>` count == `<td>` count: a header added without its cell silently shifts every column after it.
- `RSpec` is the only test framework — no Minitest.
